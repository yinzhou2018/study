## Context

当前 REPL 和 Agent 只维护一条单一用户视角的对话历史，输入中没有音区或用户归属信息。车辆状态和工具集是全局共享的，但模型无法知道“谁在哪个音区说话”，也无法判断跨音区的上下文承接关系。现有 `ToolGateway` 也不知道发起音区，无法执行音区级权限校验。

本设计在保留一条共享对话历史的前提下，引入音区/用户标签，让模型基于 System Prompt 自行判断多音区上下文，同时在工具执行层保留硬安全校验。

## Goals / Non-Goals

**Goals:**
- 让所有音区共享同一条对话历史。
- 让模型感知发言音区和用户身份，并自行判断跨音区上下文承接关系。
- 让助手回复可路由到指定音区或全车广播。
- 让工具执行层知道发起音区，用于权限和安全校验。
- 保留历史压缩后的音区归属信息。
- 在 CLI 中支持模拟音区，便于本地验证。

**Non-Goals:**
- 不引入声纹识别或账号体系，默认用户统一为 `guest`。
- 不做强隐私隔离层，个人数据先靠 System Prompt 约束。
- 不实现真实多路音频采集或 TTS 分区播放，只定义消息和路由契约。
- 不拆分为多个 Agent 实例或多个独立会话。

## Decisions

### 1. 使用内联标签，不使用 message `name` 字段

用户消息统一写成：

```text
[zone=driver,user=guest] 有点闷
```

理由：
- 对任意 OpenAI-compatible API 都透明，不依赖 `name` 字段兼容性。
- 标签直接进入模型可见内容，历史压缩后也容易保留。
- System Prompt 保持固定，Prefix KV Cache 仍然有效。

备选方案是使用 `name` 字段，但它只能表达一个维度，装不下 `user_id`，且不同客户端兼容度不一致，因此不采用。

### 2. 保留一份共享对话历史

所有音区写入同一条 `messages` 历史。模型通过标签识别不同说话人，并自行判断后续发言是否承接之前话题。

备选方案是每个音区独立会话，但那会丢失跨音区上下文，不符合本变更目标。

### 3. 模型输出前缀路由

助手回复以 `[zone=xxx]` 或 `[broadcast]` 开头：

```text
[zone=driver] 已把空调调到24度
[broadcast] 导航开始，请系好安全带
```

外层解析前缀后决定播报目标。缺省时回退到发起音区。

备选方案是由代码固定回发起音区，但那无法表达全车广播或跨音区代答，因此不采用。

### 4. 工具执行层显式传入 `requesting_zone`

`ToolGateway.execute()` 增加 `requesting_zone` 参数，与工具自身的 `target_zone` 参数区分：

- `requesting_zone`：谁在说话，由当前用户消息带进来。
- `target_zone`：工具作用在哪个物理区，由工具参数决定。

System Prompt 允许跨音区代发，但 `ToolGateway` 仍执行硬安全规则，避免模型绕过主驾专属或后排受限能力。

### 5. 历史压缩保留音区标签

压缩摘要中的每条操作记录都保留发起音区，例如：

```text
[driver] 开窗通风；[front_passenger] 调低音量
```

这样即使中间消息被压缩，模型仍能判断后续“再开大一点”指的是哪个音区的任务。

### 6. CLI 支持模拟音区

REPL 提供音区选择或切换命令，输入时自动拼上 `[zone=xxx,user=guest]` 前缀，输出时解析 `[zone=...]` 前缀并显示目标音区。

## Risks / Trade-offs

- [模型可能误判跨音区指代] → System Prompt 要求无法判断时主动确认发起音区。
- [个人数据可能串区] → 第一版靠 prompt 约束，后续可引入历史可见性层。
- [模型可能输出不符合前缀格式] → 解析层做兜底，缺前缀时回发起音区。
- [音区权限规则分散] → 权限统一放在 `ToolGateway`，不散落在 prompt 中。
- [历史压缩丢失归属] → 压缩摘要显式保留 `[zone=xxx]` 标签。
